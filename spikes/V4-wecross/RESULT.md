## Interchain mechanism (exact shapes, from `WeCrossHub.sol` and router 1.4.0)

- A FISCO contract calls `WeCrossHub.interchainInvoke(string path, string method, string[] args, string callbackPath, string callbackMethod) returns (string uid)` (also `interchainQuery`, `interchainGetBlock`). The hub stores `[uid, callType("1"=invoke), path, method, json(args), callbackPath, callbackMethod, tx.origin]` as a JSON string array.
- The router polls `getInterchainRequests(16)` (returns `"null"` when empty, otherwise a JSON array) with its admin UA, then for each request: `getXATransactionState(<target path>)` on the **target chain's** `WeCrossProxy`, calls the target `method(args)` through the target proxy with the requester's UA (looked up from `tx.origin`, field 8), calls `callbackPath.callbackMethod(bool state, string[] result)` on FISCO, `registerCallbackResult(uid, tid, seq, errorCode, errorMsg, string[] result)` on the hub, then `updateCurrentRequestIndex(index)`.
- Callback signature (sample): `function callback(bool state, string[] memory _result) public returns (string[] memory)`. Matches spec 04's `onDelivered(bool state, string[] result) returns (string[])`.
- `updateCurrentRequestIndex` and `registerCallbackResult` are **public with no access control** in the hub.

## WeCrossProxy BFS dependency and the patch

The BCOS3 proxy depends on FISCO's BFS precompile at `0x100e` in exactly these places (original line numbers): line 82 `BfsPrecompiled constant bfs = BfsPrecompiled(address(0x100e))`; 130 `bfs.link(...)` in `deployContractWithRegisterBFS`; 148 `bfs.link(...)` in `linkBFS`; 162 `bfs.list(nameToBfsPath(name))` in `readlink`; 777 `bfs.readlink(nameToBfsPath(_name))` in `getAddressByName` (used by `constantCall`, `sendTransaction`, `getXATransactionState` and the XA paths); and the `contract BfsPrecompiled` stub at the end. `WeCrossProxyEVM.sol` keeps the Apache-2.0 header, adds a NOTICE, replaces those with an owner-set `name -> address` map (`setPath`, owner-only `linkBFS` / `deployContractWithRegisterBFS`), raises the pragma to `>=0.8.0 <0.9.0`, and leaves everything else unchanged.

## Verdict

**PARTIAL (works with fixes; relayer stays primary until M12 proves the EVM side)**. Router 1.4.0 + BCOS3 stub (java-sdk 3.6.0) run against FISCO 3.17.1: deployment of proxy/hub, resource listing, calls and transactions through the router, and interchain pickup all work; no stub patch to a newer java-sdk was needed. The account manager needs a PKCS#1 key. The EVM half (our stub + patched proxy on Base) is the remaining work; the patched proxy already compiles and passes its tests.

## Traps (one line each, with the default to apply)

1. Account manager crashes on an OpenSSL 3 RSA key (PKCS#8): generate with `openssl genrsa -traditional` or convert with `openssl rsa -traditional`; do it in the image build.
2. The router will not start until the account manager answers: compose `depends_on` with a healthcheck on `:8340`.
3. Router and account manager use about 1.3 GiB + 0.65 GiB with JVM defaults: set `-Xmx512m` (router) and `-Xmx256m` (manager) in compose and measure again in M12.
4. `bcosDeploy` compiles with solc 0.5.2 on the router: never deploy our contracts through WeCross; deploy with Foundry (0.8.28) and register them (`bcosRegister` / BFS link) or let the stub list them from BFS.
5. A `string[]` argument goes through the router as one JSON array string (`["a","b"]`); the EVM stub must decode it the same way.
6. One undeliverable interchain request (unknown target chain, missing target proxy) blocks the hub queue forever (the router never calls `updateCurrentRequestIndex`): the relayer watchdog (spec 05, `BRIDGE_WATCHDOG_S`) must not depend on hub progress, and BaseOutbox must target only `payment.base.inbox`.
7. `WeCrossHub.updateCurrentRequestIndex` and `registerCallbackResult` are callable by anyone on FISCO: a griefer can skip requests or write fake callback results; default: treat hub callbacks as hints only (BaseOutbox `markDelivered` stays restricted to the router/relayer accounts, first write wins, as spec 04 says) and consider FISCO method ACLs (`ContractAuthPrecompiled.setMethodAuthType`) on the hub in M12.
8. The interchain requester (`tx.origin` of the `interchainInvoke` tx) is mapped to a universal account in the account manager; that UA needs an EVM chain account for `payment.base` (`WECROSS_BASE_KEY`). Default: BaseOutbox's enqueue transactions are sent by one dedicated FISCO account registered in the account manager with the Base key as its EVM chain account (not verified end to end without a Base chain).
9. The stub generates its own FISCO admin key under `conf/chains/<chain>/admin/`: whitelist it through the committee (spec 04 deploy ACL) or replace it with a key from `.env` before deploying the proxy/hub.
10. The patched proxy needs `via_ir = true` under 0.8.28 (stack too deep in the original XA code); keep `via_ir` scoped to that one contract's profile.
