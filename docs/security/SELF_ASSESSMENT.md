# Security self-assessment

Praetor lets an AI agent move a user's money, so the design question is not "is the agent trustworthy" (it is not) but "what is the worst the agent, or anything around it, can do". This document answers it with evidence from the code as built: the permission tiers and the contract function that enforces each, the nineteen invariants with the tests that prove them, the threat model, the known risks, and the results of the tools. Chinese version: `docs/zh-CN/SELF_ASSESSMENT.md`. Architecture: [docs/ARCHITECTURE.md](../ARCHITECTURE.md).

Snapshot: 2026-10-17, end of M17. Milestones M12 (WeCross gate), M13 (web app), M14 (mini program), M15 (F10, Guomi smoke), M16 (live run, red team) and M18 (deployment rehearsal) were still being built in parallel; sections that depend on them say so.

## 2. Permission tiers

Every execution of a Praetor account passes `MandateHook.preCheck` (I1), whoever signed it. The hook's single evaluator, `DecisionLib.evaluate`, returns for each call a reason and a tier; `check()` and `checkBatch()` expose the same evaluator as views, so a refusal recorded by `RefusalLog` always carries the reason the hook computed (I11). Rule of thumb everywhere: **stricter needs fewer signatures than looser.**

Exact thresholds as built (`contracts/base/src/hook/ConsortiumLib.sol`): a status change is "tightening" only when the new status is stricter than the stored one; the same or a looser status needs 2 signatures. Asset changes count as loosening when the status becomes less strict, the bank's max weight rises, or the kind changes. A heartbeat is accepted with any one member and at most one day of validity (`MAX_HEARTBEAT_TTL`). `Anchor` accepts any two members; that the bank is one of them is the operator service's policy (D41), not a contract rule.

Reason codes as built: the hook returns the reasons of spec 02 in the decision order of spec 03. Two codes of the frozen protocol are never returned by `check()`: `TIER2_REQUIRED` (14) and `TIER2_INVALID` (15). An invalid approval does not produce a refusal reason: `registerApproval` and `applyOwnerAction` revert with a custom error (`BadOwnerAuth`, `BadSoter`, `DigestUsed`, `BadExpiry`, `SlotBusy`, `SoterNotEnabled`, `BankRequired`), so nothing is registered and the payment stays refused with its original T2 reason (D65).

## 5. Known risks

Items 1 to 17 are spec 08's list, updated to the build; items 18 and later were added during the build or found in M17.

1. **Agent key.** A compromised agent TEE or leaked agent key can act inside the mandate until the owner revokes it or the consortium freezes the account. Bounded by the hook and the bank caps.
2. **SOTER trust.** SOTER approvals trust Tencent's unsigned `is_ok` and the attester's code. Bounded by the binding, the counter, the one-hour expiry, the hard cap and the bank caps.
3. **One team runs the demo consortium.** In production bank, regulator and operator are independent organisations with their own HSMs.
4. **Unbacked tokens.** tXAU and tXAG are demo tokens; production needs a regulated custodian with proof of reserves.
5. **Mocked payouts.** The payout partner and the Alipay+ and WeChat Pay gateways are labelled mocks (the payout partner runs the real `ant-intl-alipayplus-mcp` client against the mock gateway). Production needs a licensed PSP; stablecoin payouts only where licensed, never for mainland China residents (`JURISDICTION_BLOCKED`).
6. **Oracle feeder.** A single key, bounded to 25 % per update. Without `PYTH_API_KEY` the feeder pushes seeded prices flagged DEMO (D13, BLOCKERS B2), and no service refuses DEMO mode in prod.
7. **RefusalLog link.** The link from a `Refused` record to its userOpHash is the reporter's claim; the reason is not. The bundler writes RefusalLog only for an op refused in its pre-check that then failed on-chain.
8. **WeCross.** WeCross 1.4.0 is unmaintained upstream; the EVM stub is new code (`wecross/evm-stub`, JUnit vectors checked against viem).
9. **Freeze blocks the owner.** A consortium freeze also blocks the owner's own payments and module changes (D19): a regulated account by design.
10. **Mini program.** The mini program runs on a test account in debug mode; publication needs a registered company and ICP filing. Built in M14.
11. **30-day epochs.** Monthly budgets use `block.timestamp / 30 days`, not calendar months: up to two monthly budgets across a boundary.
12. **ERC-3643 agent role.** The bank's token agent key can force-transfer or burn tXAU and tXAG of any holder (the standard's recovery power), outside the hook (`Tokens.t.sol`, `test_agentForcedTransferBurnAndRecovery`).
13. **Compromised mcp.** mcp is the only service allowed to call `sign-userop`; compromised, it acts inside the T1 mandate. See also item 19.
14. **Compromised attester key.** It can approve T2 payments for every SOTER-enabled account until any one member deactivates it.
15. **Sealers.** In the demo the operator runs 2 of the 4 FISCO sealers and can halt the consortium chain; production gives each member its own sealer and adds a fourth member.
16. **SOTER counter on iOS.** If the counter does not increase on iOS, the hook's `soterCounterStrict` (an immutable constructor flag, true by default through `SOTER_COUNTER_STRICT=1`) must be deployed as false; replay stays impossible because each approval's digest is single use.
17. **WeIdentity REST** is custodial and unauthenticated; it runs on its own `identity` network joined only by the bank, MySQL and one FISCO node (D29, `test/infra/compose.test.ts`).
18. **WeCross transport notes** ([wecross.md](wecross.md)): one undeliverable request can stall the hub queue (the watchdog does not depend on it); two hub setters have no access control; on a failure the router logs a chain account's private key (kept on the host or CVM only); the router RPC is plain HTTP on the Docker network; the bridge-relayer holds the WeCross router's FISCO key in `BRIDGE=wecross` mode (D42).
19. **`INTERNAL_TOKEN_API` reaches the agent key.** mcp's `POST /internal/resubmit` (used after a human approval) submits up to eight calls for any account with the agent key, behind `INTERNAL_TOKEN_API`, which the api, the notifier and mcp share. A compromised api or notifier can therefore act inside the T1 mandate of every account, like a compromised mcp. Likewise agent-runner holds `INTERNAL_TOKEN_MCP`, which mints an agent bearer for any account. The hook still bounds every call. A narrower route (resubmit only a call with a live approval) is a follow-up.
20. **Shared internal tokens.** `INTERNAL_TOKEN_MEMBERS` is shared by the api and the three member services, `INTERNAL_TOKEN_BUNDLER` by every bundler caller, `SESSION_SECRET` by the api and mcp. Consortium signatures still need a staff passkey assertion over the exact digest, except four automated, rule-checked signatures: the operator's heartbeat, the bank's KYA after its own checks, the bank's owner-action co-signature after its rule checks, and the bank's anchor co-signature after recomputing the chain (D24, D26, D41).
21. **Web hardening, as built.** No Content-Security-Policy or other security headers (Caddy, api, web app), no Origin check on state-changing requests (CSRF relies on `SameSite=Lax` plus the CSRF token), no rate limit in the api, member services or KYC mock, production source maps shipped, and `/api/console/agents` lists up to 50 accounts with their status and KYA attributes without authentication (the same data is public on Base).
22. **What you see is what you sign, partly.** The web app recomputes the Tier2Approval digest from the request's preimage before the passkey signs; it signs owner actions, the WeChat link confirmation, the deployment userOp and console proposals as the api returns them. A compromised api could get a passkey signature over a different owner action than the one shown; the bank's rule checks (D26) and its co-signature bound the damage (bank caps, our modules only, the KYA agent key) but do not stop, for example, an extra payee. The web app is still being built (M13).
23. **Staff WebAuthn details.** Member services accept high-s P-256 staff signatures and do not check the signature counter. Malleability is not forgery and challenges are single use; low impact.
24. **In-memory state.** Staff sessions and challenges, the bank's quote nonces, the WeChat link sessions and agent-signer's rate limit live in memory and reset on restart.
25. **Prod refusals are per service.** `packages/config` refuses simulator attestations, the fake Tencent, the fork, default passwords and an unthrottled sandbox, but only the bundler, the bridge-relayer and the member services load it; agent-signer, soter-attester, the bank and agent-runner carry their own checks (simulator, fake Tencent, WeChat API base, fake LLM); oracle-feeder's DEMO mode is not refused; `SANDBOX_RATE_LIMIT_PER_HOUR` is required in prod but nothing enforces it yet (the sandbox is not built).
26. **KYC paths.** The EUDI path trusts the EU verifier backend for the credential signature and yields kycLevel 1 without name screening (D30); the vendor HMAC covers the body but no timestamp (replay is stopped by the session state machine); the KYC vendor is a labelled mock whose decision is always "approved" (the bank still checks liveness, age, sanctions and jurisdiction).
27. **Pseudonymous attributes on Base.** KYA attestations put kycLevel, riskProfile and a two-letter jurisdiction per account on Base, and the ERC-3643 identity registry stores a country code (D69).
28. **USDC is implicitly approved** (D21): the consortium cannot delist USDC itself; Circle's own controls apply.
29. **Process.** `make slither` is red because of the vendored WeCross proxy (all findings triaged, D66); gitleaks run inside a git worktree reports "no leaks" even when its git scans fail; dependency advisories of [deps.md](deps.md) are not upgraded yet.
30. **Test-only services in the default profiles.** The scripted fake LLM starts with the `agent` profile; agent-runner refuses `FAKE_LLM_URL` when `PRAETOR_ENV=prod`, so a prod deployment must leave it unset.
